### 1.5 API contract enforcement and drift

The contract is distributed across several layers:

- `opsnexus-api/api/openapi.yaml` and `api/schemas/*.yaml` define a partial OpenAPI 3.1 contract. It includes SSE, registration, agent telemetry, overview, health, metrics, analytics, alerts and alert-rule routes. The inspected OpenAPI file does not visibly cover every runtime route, including the notification and token surfaces present in `internal/server/server.go`.
- `opsnexus-common/models` defines Go `Agent`, `AgentRegistration`, and `AgentTelemetry` models shared by agent/backend. It does not generate from OpenAPI.
- The agent collector defines additional concrete metric structs in `internal/collector`; telemetry is transported through the common `map[string]any` envelope.
- The backend defines handler/repository response structs in `internal/agent`, `internal/telemetry`, `internal/observability`, `internal/alerting`, `internal/notifications`, `internal/auth`, and `internal/events`.
- The dashboard manually defines TypeScript interfaces in `src/types/api.ts` and API calls in `src/api/*.ts`. No generated-client or OpenAPI codegen configuration was found.
- No `.github/workflows` exists in any repository, so OpenAPI validation, backend-vs-contract route checks, dashboard type generation, and agent payload validation are not enforced in CI.

Concrete drift opportunities include the dashboard's manually maintained `DiskPartition` fields, backend telemetry/observability response structs, OpenAPI's narrower endpoint inventory, and the use of `map[string]any`/JSONB for the central payload. The agent and backend do share the common envelope, which reduces one class of drift, but common models are not a substitute for validation of the public HTTP schema.

Contract enforcement is therefore **verified absent**. Silent drift can occur at API definitions, backend handlers, dashboard interfaces, and deployment configuration boundaries.

### 1.6 Security baseline

| Control | Classification | Exact evidence |
|---|---|---|
| Authentication default | **HIGH RISK** | `internal/config/config.go` sets `APIAuthEnabled` only when `OPSNEXUS_API_AUTH_ENABLED == "true"`; `.env.example` sets it to `false`. |
| CORS default | **HIGH RISK** | `config.Load()` defaults `CORSOrigins` to `"*"`; `middleware.CORS` emits `Access-Control-Allow-Origin: *`. |
| TLS | **NEEDS HARDENING** | Agent default URL is HTTP; Compose database URL uses `sslmode=disable`; deployment exposes plain HTTP ports and Nginx listens on port 80 only. README says TLS belongs to an external reverse proxy. |
| Token storage | **SAFE / NEEDS HARDENING** | `internal/auth/auth.go` hashes bearer tokens with SHA-256 before querying `api_tokens`; expiry and enabled checks exist. SHA-256 is acceptable for random API tokens but token lifecycle/audit policy is not externally governed. |
| Token exposure | **NEEDS HARDENING** | `APIToken.RawToken` is intentionally JSON-visible on creation; source says “Only returned once.” Dashboard has token API calls but no visible bearer attachment/storage strategy. Logs/tests must ensure raw tokens never appear. |
| Webhook SSRF/egress | **HIGH RISK** | `internal/notifications/webhook.go` posts to a caller/database-supplied URL using `http.DefaultClient` with no visible scheme allowlist, private-IP blocking, DNS rebinding defense, timeout policy, or egress proxy. |
| Rate limiting | **NEEDS HARDENING** | `middleware.RateLimiter` exists and is applied to many writes, but it is in-memory, keyed by `RemoteAddr`, not distributed, and some reads/public endpoints are not limited. |
| Secret loading | **NEEDS HARDENING** | Secrets come from environment/database records; `.env` is ignored and `.env.example` is safe-looking, but there is no secret manager, production validation, or rotation workflow. |
| Secret logging/redaction | **UNKNOWN** | Structured logging exists, but no organization-wide redaction test/policy was found. Notification errors and request logging need explicit review. |
| Public endpoints | **NEEDS HARDENING** | Auth middleware intentionally permits `/health` and `/api/v1/events`; when auth is disabled it places `RoleAdmin` in context for all requests. |
| SSE authentication | **HIGH RISK** | Backend explicitly allows `/api/v1/events` before bearer validation; browser `EventSource` in `src/api/events.ts` cannot add an Authorization header. The stream is therefore public by design in the current implementation. |

The implementation has good foundations—hashed tokens, role checks, expiry, request IDs, rate limiting, and HMAC signing in the webhook provider—but the default deployment profile is not a safe production baseline.

### 1.8 Deployment reproducibility

`docker-compose.yml` has these runtime properties:

- Build context for backend and dashboard is `..`, which resolves to the OpsNexus workspace parent when run from `opsnexus-deployment`.
- Backend Dockerfile path is `opsnexus-deployment/backend/Dockerfile`; dashboard Dockerfile path is `opsnexus-deployment/dashboard/Dockerfile`.
- Backend Dockerfile copies `opsnexus-common` and `opsnexus-backend` from the parent context, runs `go mod download`, and builds `./cmd/server`.
- Dashboard Dockerfile copies `opsnexus-dashboard`, runs `npm ci`, and runs `npm run build`; the final image is Nginx serving static assets.
- No custom image names are declared; services are built locally and named by Compose containers `opsnexus-backend` and `opsnexus-dashboard`.
- PostgreSQL is `postgres:16-alpine`, with a named `postgres_data` volume and a `pg_isready` healthcheck.
- Backend waits for PostgreSQL health; dashboard waits only for backend service start, not backend readiness.
- Backend maps `${OPSNEXUS_PORT}:8080`; dashboard maps `5173:80`; PostgreSQL is internal-only because it has no host `ports` mapping.
- All services share a bridge network; the backend reaches PostgreSQL at service name `postgres`.
- No migration command, migration volume, entrypoint migration step, or migration health gate appears in Compose/Dockerfiles. The SQL migrations remain in backend source and are compiled into neither an explicit migration job nor a documented startup process.
- `.env.example` supplies interpolation inputs, but the default values disable auth, allow wildcard CORS, and use development database TLS settings.

Read-only `docker compose -f docker-compose.yml config --no-interpolate` succeeded. It rendered the expected three services, build contexts, dependency condition, network and volume. It also rendered the local absolute context `/home/chandanraj-m/OpsNexus`, proving reproducibility currently depends on the sibling-repository workspace, not on a clone of deployment alone. A fresh clone of only `opsnexus-deployment` cannot build the stack; a fresh clone of the full workspace at compatible refs can.

Deployment reproducibility is therefore **partially verified**: the Compose graph is syntactically renderable and internally coherent, but it is not a standalone repository deployment and lacks migration/readiness/production validation.

- **Build dependency:** deployment Dockerfiles require `opsnexus-common`, `opsnexus-backend`, and `opsnexus-dashboard` at paths relative to the workspace parent.

## 6. Recommended remediation

1. Correct the report/documentation facts first: backend URL, agent env names, deployment tag semantics, and release matrix.
2. Establish API ownership and generate/lint/validate the contract before changing payload models.
3. Add CI to each repository, beginning with format/lint/test/build and API/Compose/docs validation.
4. Add cross-repository compatibility fixtures for agent/common/backend/API/dashboard.
5. Define production security profiles and test auth-on, explicit CORS, TLS boundary, token handling, SSE access, webhook egress and rate limits.
6. Make deployment reproducible either through published immutable images or a documented full-workspace checkout; add migrations, readiness, smoke and rollback checks.
7. Add dashboard tests and resolve browser authentication/SSE design.
8. Reconcile component tags and publish a platform release only after the compatibility and deployment gates pass.

## 7. Dependency/order of remediation

```text
Truthful inventory and owners
        ↓
API/version policy ───────┐
        ↓                 │
CI and contract gates ───┼──> cross-repository compatibility
        ↓                 │              ↓
Security production profile ┘     deployment smoke/migrations
                                               ↓
                                  dashboard auth and release
```

Do not begin a broad source refactor. The order minimizes repeated work: contract and version decisions precede generated types; CI precedes branch protection and release; security/deployment validation precedes enabling production auth; dashboard authentication is resolved before a platform release claims secure operation.

## 8. Risks if remediation is delayed

- A README consumer will export unsupported agent variables and silently run with localhost/10-second defaults.
- A dashboard can appear healthy with auth disabled while failing or becoming unsafe when bearer auth is enabled.
- OpenAPI, backend, common models and dashboard types can drift without detection, producing runtime 4xx/5xx or misleading metrics.
- Wildcard CORS, auth-off deployment and public SSE can expose operational data or management surfaces if deployed without an external security boundary.
- Notification URL handling can become an SSRF path and may reach internal services.
- A fresh deployment clone cannot build without sibling repositories and may start without applying database migrations.
- The organization may publish a misleading v0.6.0 status or incompatible component combination.
- Without CI, regressions and secret/artifact mistakes can reach `main` and releases without evidence.
